# 设备无预置凭据 Onboarding 方案与实现边界

状态：**设备方已评审通过；仓库代码与 REST 契约已按此方案改造**（2026-09-29）。目标 AWS 部署和真实设备联调：**NOT RUN / NO RECEIPT**。

## 已确认的设备约束

设备出厂只有印刷序列号，没有预置平台 Token，也没有屏幕、动态二维码、蓝牙、热点或现场再次写入 Token 的能力。设备软件必须能在本地生成并持久保存 RSA 2048 位或更强私钥、生成并签名 PKCS#10 CSR、用私钥签名状态轮询，以及安装返回的证书。设备方已认可：请求与实物的对应关系依靠既有线下管理制度与管理员审批，不把印刷序列号或 CSR 本身当成实物身份证明。仓库无法用接口设计单独消除伪装设备或抢先申请风险。

## 实际流程

1. 运维在库存登记设备印刷序列号，并保留安装记录。设备本地生成私钥与 CSR；私钥不离开设备。
2. 设备向 `POST /api/v1/device/onboarding/request` 提交设备资料和 CSR，**不需要 Bearer Token**。服务端验证 CSR 自签名、RSA 长度、库存状态与限流。相同序列号且相同公钥的待审核申请幂等返回原 `requestId`；不同公钥冲突返回 409。
3. 管理员在线下核对实物和申请记录，在管理后台审批或拒绝。后台申请 DTO 展示 CSR 公钥指纹；该指纹用于辨别申请及重试，不单独证明设备身份。
4. 审批后 Worker 使用项目 CA 对原 CSR 公钥签发设备证书、注册 AWS IoT、绑定单设备策略。新流程不生成、不存储、不返回设备私钥；发证后检查证书公钥与 CSR 是否一致。
5. 设备以 `requestId` 和本地私钥签名轮询 `GET /api/v1/device/onboarding/status`。签名覆盖方法、路径、申请 ID、毫秒时间戳和随机数；服务端验证五分钟时间窗与随机数唯一性。批准且发证完成后只返回公钥证书、MQTT Endpoint 与初始配置。设备安装前核对证书公钥与私钥匹配。
6. 设备用新证书发送首个合法 Heartbeat 后完成 Onboarding。24 小时截止、一次性领取、丢包撤证重签等既有恢复规则仍沿用；超时重新申请可使用新 CSR，无需新 Token。

签名详细格式、请求与响应示例以 [Onboarding API](./api/onboard-api.bio-nexa.com.md) 和 [可执行 OpenAPI](../contracts/rest/device-onboarding-api.json) 为准。旧 Token 分支仅作为迁移兼容，不能作为新设备的前置步骤。

## 已知边界和后续验收

- 线下制度必须防止可见/可猜序列号被第三方抢先申请，管理员须确认申请对应现场实物后审批。服务端的 CSR 自签名只证明申请者持有私钥，不能证明该私钥由指定实物生成。
- 设备时钟必须能可靠同步，签名时间戳允许 ±300 秒。设备需要持久保存私钥与 `requestId`，证书领取前后发生掉电时按重试/撤证重签流程恢复。
- 旧版证书轮换接口仍可能生成并下发新私钥。本次“私钥不离设备”只适用于**首次 CSR Onboarding**；若要扩展至全生命周期，轮换接口需单独改成 CSR 协议。
- 本地测试只验证仓库实现。AWS 项目 CA、IoT Core、API Gateway、管理后台实际部署和真机首次 Heartbeat 仍需隔离环境、设备方与运维方联调后留存证据。
