# QA-09 精确采集器小批读取与总时限复验

前次应用 `41ee358f` 的 R1 中，12 条采样 PATCH 的普通、精确及一次精确恢复均发生日志读取超时，阶段 Gate 为 PARTIAL。业务与清理通过不能替代阶段完整性。本轮修改本地只读采集器，不修改应用候选、部署开关、IAM/KMS、数据库或容量；旧失败回执保持原字节。新 SHA 目标对照必须另行执行。[实施记录](../audit/QA-09-精确采集器小批读取与总时限实施记录-2026-10-12.md)。

## 固定读取预算

| 项目 | 限制 |
| --- | --- |
| 总时限 | 每次采集器调用共享单调时钟120秒，覆盖两个日志组、所有批次、分页及关联处理；不是每批120秒 |
| CLI 子进程 | 最多15秒，取15秒与剩余总时限的较小值 |
| CLI 网络 | connect=3秒，read=10秒，AWS_MAX_ATTEMPTS=1，关闭自动分页 |
| 调用次数 | 整次采集最多40次，单查询最多20页；达到上限且仍有分页令牌则 PARTIAL |
| 精确 Lambda 批次 | 最多19个唯一自有 invocation，每批最多3个，串行；19个分为7批，末批1个 |
| 单页 | 最多1000事件、4MiB响应，令牌最多8192字符；重复或非法令牌失败 |

普通模式也共享同一总时限和调用上限。Gateway 读取仍为原子流程中的同一固定时间窗；精确 Lambda 查询按经原 Gateway 唯一证明的 invocation 顺序分批，字段投影只接受该批自有 request ID。不得扩展时间窗、扫描其他日志组、重新执行业务或增加自然冷样本。

任一读取失败即停止后续页/批次；尚未开始的日志组标记 `LOG_READ_NOT_STARTED`。已经取得的结果和全部原请求行保留，缺失结果不填零。CLI 超时、总时限、权限、SSO过期、限流、分页不完整、响应非法及客户端不可用均使用固定安全错误码，不写 stderr、令牌或业务载荷。错误分类是现象标签，不是云端或网络节点归因。

新回执 `logReadBudget` 记录固定预算、安全逐调用结果和全局错误，另绑定 `readerSha256`。输出仍使用新文件且禁止覆盖；进程退出0只表示回执已写出，只有预算、关联和阶段门禁共同通过才可继续。

## 源字节和恢复回执

普通与精确模式继续共用 `qa09_observer_cost.py` 的严格 schema2 白名单；唯一 COMPLETE 摘要、时间/操作/请求关联、自有段守恒及原阶段阈值不变。新读取成功不能放宽这些门禁。

精确模式兼容历史未提供 `--exact-sha256` 的调用，但**本轮目标流程必须提供原回执字节哈希**；新增预算检查拒绝缺失该绑定的精确结果。原子流程的字节哈希仍由 prior 的 `sourceReceiptSha256` 双向核对。

```sh
python3 scripts/collect-qa09-contract-correlation.py CHILD.json PATCH-ORIGINAL.json --cold-sampling --observer-cost --owned-boundaries
# 计算 PATCH-ORIGINAL.json 的 SHA-256，填入下方，保留原文件。
python3 scripts/collect-qa09-contract-correlation.py CHILD.json PATCH-EXACT.json --cold-sampling --observer-cost --owned-boundaries --exact-from PATCH-ORIGINAL.json --exact-sha256 <原回执64位SHA256>
node scripts/check-qa09-log-read-budget.mjs CHILD.json PATCH-EXACT.json PATCH-ORIGINAL.json
```

基线去掉 `--cold-sampling`；审计 GET 加 `--audit-get`，不要求合同摘要；R0 不加 `--observer-cost --owned-boundaries`。普通成功回执也执行预算检查，命令只传 CHILD 和关联两个路径。恢复必须另存新文件，记录原/恢复 SHA-256、采集器/reader/projector 字节及命令。普通失败可按既有授权执行一次精确恢复；精确恢复仍 PARTIAL 时停止恢复，不循环重试、不补业务请求、不将已通过子集当作整组通过。

## 新 SHA 顺序及入口 Gate

1. 人工通过 GitHub Desktop 推送新本地提交；核对同完整 SHA 的 CI、默认关闭部署、19实际工件、发布输入与实际配置。保持 ApiFn512MiB/reserved12/pool1、静态连接预算63≤70。旧 SHA 的工件和失败回执不能充当新 SHA 回执。
2. 生成新输入：`node scripts/analyze-qa09-contract-observer.mjs --prepare <完整新SHA> <新输入.json> --owned-boundaries`。沿用[原复验手册](QA-09-自有边界摘要接线与目标复验.md)的所有阶段、SSO余量、受控 Worker、未知启动和清理约束。
3. R0：engine/preconnect/account/detail/public=true、observer=false。新前缀执行原业务预算（并发≤6、6次基线、最多12次独立 PATCH），原父子清理、独立空集、容量和完整阶段全部通过，才能启动 R1。
4. R1：仅 observer=true，另一个新前缀；采集 PATCH 时要求 observer/schema2，其他输入及业务预算相同。每份用于阶段 Gate 的关联回执先通过 `check-qa09-log-read-budget.mjs`，然后执行原 `check-qa09-contract-phases.mjs` 及匹配自然冷分析。不得改旧封存 helper；新 helper 清单须绑定 reader、预算检查器及全部依赖。
5. R1 清理/独立空集闭合后，同 SHA 关闭恢复 observer/public/detail/account/preconnect=false、engine=true；核对19工件、实际配置、最终容量、数据库空集、S3当前/历史版本及全部精确自有 Build 终态。任何失败仍优先执行原清理及关闭恢复；未知 StartBuild 不重放。

只读容量预检仍不可在未知启动后擅自重复。预算检查仅证明读取回执完整及源码字节一致，不证明真实业务、阶段、P95或整体 QA-09 已验收。缺自然冷匹配则保持 NOT RUN。TCP/TLS 长尾与应用阶段独立分析，本轮不追加网络探针。
