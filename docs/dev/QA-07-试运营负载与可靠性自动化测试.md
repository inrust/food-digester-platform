重复数=唯一Telemetry数的5%，显式延迟乱序数=2%；重复沿用原始ID/seq/时间/内容，不另造业务消息。选定消息延迟到同设备下一序号之后；历史补报本身另有时间乱序。短时突发为每设备3条/秒，正常为每设备0.1条/秒。所有历史窗口仍以10秒间隔生成样本；quick跳过每小时其余3580秒，不能宣称连续24小时全部处理或24小时稳定运行。`full`可执行完整补报，但仍是加速本地试验，不是AWS实跑或24小时墙钟 soak。

输入计划独立于生产数据库生成；入队生产者按单调时钟调度，消费者独立运行，不能以Worker处理时间反向拖慢生产速率。报告记录配置、实际处理量、最大积压、总执行时间、原始延迟样本及P95。调度采用压缩后的等价比例；本地CPU、PGlite与内存端口的吞吐不代表AWS容量。

## 24小时历史补报边界

初次探针发现旧管线将过去超过300秒的Telemetry送入CLOCK_SKEW隔离。2026-10-01用户明确要求在QA-07修复，事实源为 [补报策略1.0.0](../../contracts/mqtt/telemetry-backfill-policy.ts)：Telemetry `iotReceivedAt - meta.ts` 最大86400秒，含精确边界；未来时间仍受配置容差约束，默认300秒，含边界。其他Topic继续保持双向容差。无设备端可选标记、额外Topic或绕过身份、Schema、audit.hash/receipt校验的路径。

真实管线验证24小时及未来300秒边界接受，越界1毫秒和过旧Heartbeat隔离且原文留存；坏audit.hash的历史Telemetry仍拒绝。业务保持原始设备时间，聚合归入历史小时，最新API指标不被历史桶覆盖。尚未部署。

## 自动断言与计时

- 正常Telemetry：从消息实际入队单调时刻起，经过队列等待、生产Ingestion/业务事务，再调用真实管理后台Device Console Handler，确认最新小时桶的currentAmp平均值与独立输入账本一致，记录到API返回的墙钟耗时。P95采用nearest rank，≤5000ms；不含网络HTTP、AWS Broker/队列传输。
- Command：十台设备经Heartbeat确认ONLINE，从交给生产发布器开始，到注入MQTT端口完成及发布状态/attempt/audit持久化返回为止，P95≤3000ms。合法重复发布不再调用MQTT；到期只迁移和审计一次，迟到ACK保留事件但不改变TIMED_OUT。
- Worker暂停200ms期间生产者持续入队，业务/receipt数量不变，恢复时必须存在积压；一个Dispatcher瞬时失败须无receipt写入并重试成功。单条指定缺口先留待恢复账本，后继已入业务时必须存在对应数据库gap；补齐后所有gap解除、待处理账本清空。
- 独立一致性校验器按输入去重前的唯一Telemetry逐条计算UTC桶sampleCount、currentAmp avg/min/max，与真实聚合表全量比对。全部receipt键唯一，数目与计划吻合；正常合法消息不得隔离。
- Outbox队列发送失败重试、Manifest失败重试；所有Telemetry归档原文逐条与输入完全一致，压缩对象SHA-256与Manifest吻合。
- 指定Customer/device/topic/time/seq范围由真实Replay Worker筛选；经过真实Replay Ingress Sink恢复当前ACTIVE证书身份后重入Ingestion。范围内全部发出，范围外跳过，receipt/outbox/聚合无新增，已完成任务再执行无发送。

## Gate、报告与清理

[runner](../../scripts/run-reliability-suite.mjs)只接受完整通过的两项真实集成测试与唯一QA07随机前缀回执；核对负载计划、处理数、重放/故障证据、缺口账本、原始延迟样本并复算P95。源代码、迁移、契约、依赖、测试与脚本Hash运行前后必须一致。失败写FAIL回执，临时JSONL/报告finally删除；数据库finally关闭，内存队列/对象清空。不执行生产扩缩容、资源告警、部署或值守。
