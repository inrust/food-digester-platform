# QA-09 性能修复分阶段部署与回滚

日期：2026-10-03。此文是实施与复验操作说明；代码完成不代表共享环境已部署或 Command P95 达标。远程推送由人工 GitHub Desktop 执行。

## 开关与顺序

`FDP_QA09_ROLLOUT_PHASE` 支持 `baseline`（默认）、`observability`、`capacity`、`immediate`。GitHub Actions 从同名 Repository Variable 读取；本地 CDK 包装器从环境读取。未知值拒绝执行。容量阶段依赖请求日志，即时发布依赖容量阶段。基线不会自动启用新增共享资源。

1. 只读核对目标版本、19 个 Lambda 工件和 AWS 账号/区域。保存 API Gateway 区域级 Account 原 `cloudWatchRoleArn`、当前模板、并发和数据库参数；该 Account 是区域共享设置，确认单一管理者并评估其他 API。
2. 审阅并合并 `infra/iam/QA09-AdminGatewayLogsBoundary-additions.json` 到当前 ServiceBoundary。补丁只允许指定 `fdp-test-admin-gateway-logs-role` 的 DescribeLogGroups（只读枚举，Resource *）及唯一主日志组的 DescribeLogStreams/GetLogEvents/FilterLogEvents（组/流两种精确 ARN）。本轮已应用默认 v8，原 v3 保留。避免替换整份线上边界。核对 KMS/日志读取身份的限定解密授权。
3. `FDP_QA09_ROLLOUT_PHASE=observability node scripts/esgiot-cdk.mjs diff AppDependencies`。审批实际 diff 后部署：7 天 KMS 加密访问日志，仅关联 ID、模板路径、HTTP/集成状态及耗时；execution logging/dataTrace 关闭。产生真实请求，按 Gateway requestId/integrationRequestId 与 Lambda awsRequestId 逐请求关联 500、429、限流和未处理异常。日志无敏感数据才进入下一阶段。
4. 用同样的 diff/部署流程进入 `capacity`：Admin 并发 12，Admin 与 15 个 DB Worker pool1；Device/Onboarding 保持 pool2。确认真实普通连接槽位至少 62，连接错误、池等待及旧执行环境空闲连接可控。真实 Prisma 根查询/事务/错误回滚与 API 联合压测须另取回执。
5. 进入 `immediate`：专用 KMS SQS/DLQ、batch1、无 batching window、partial batch failure；Publisher 并发 2。API 在事务中持久化 Command、审计及 Outbox，提交后立即发送 commandId。分钟扫描补偿保留。拒绝先 MQTT 后提交。

## 数据库预算

18 个 DB Lambda 统一从 `infra/src/database-capacity.ts` 计算并发与 pool 上限，未知 DB 函数拒绝配置。即时阶段稳态 44 条，加运维预留 8、空闲/轮换重叠预留 10，共 62，普通槽位规划 70，余量 8。默认基线旧配置需求 80，不能被误当作满足新预算。pool 默认仍为 2；开关启用才按函数注入 1/2。连接超时 5 秒、空闲超时 10 秒。

AWS 内固定只读探针命令：`node scripts/run-qa09-pool-readonly.mjs <新回执路径>`。使用既有受控 CodeBuild 项目、固定源码、RDS TLS、服务器只读事务，拒绝其他 application_name。验证 24 个并行调用的单连接串行化和预期事务错误后的恢复；不等价于真实 Prisma/API 容量验收。

## 故障与回滚

SQS 发送失败保留已提交 Command/Outbox，分钟扫描补偿；API 不因通知失败回滚成功事务。通知重复、并发扫描共用 120 秒持久租约；发布不占 DB 事务连接。旧租约持有者无法覆盖新持有者结果，ACK 终态不被发布结果覆盖。进程在 MQTT 成功后、落库前崩溃可能重复投递；保持同一 meta.id，设备端必须幂等，不承诺 exactly-once。

即时发布异常时先停专用事件源、保留队列/DLQ与证据，退回当前代码的 `capacity` 阶段，继续分钟补偿并核对全部未终结命令。主队列设置 RETAIN；删除栈开关不会自动抹去主队列，后续重新接管须先解决同名 retained 资源。DLQ 删除前导出本轮关联证据并核对持久 Outbox，不读取/清空共享队列。不可直接回滚到不识别 PUBLISHING/租约的旧版本。

容量阶段出问题先暂停负载并诊断，不能盲目恢复旧 pool2 配置（原预算 80 超出普通槽位 70）。任何回退并发/池组合都需重新计算预算、等待旧连接回收并监测 RDS。日志回滚需恢复区域 Account 的原 ARN，保留日志组/KMS Key；仅在新角色退出使用后撤销对应 Boundary 补丁。

## 验收出口

需要部署后同一版本回执：请求关联完整；无池耗尽/连接预算越界；真实 MQTT 速率、Telemetry API 可见 P95、在线 Command P95≤3000ms；通知重复、发送失败、租约恢复、ACK 竞态与队列重投；自然生命周期、全部有效写权限、全业务 E2E/117 语义行为与安全。未执行项继续 NOT RUN / NO RECEIPT。不得将本地绿色或单连接只读探针作为完整 QA-09 PASS。

### Command 队列 Key Policy 前置（真实拒绝修复）

消费者的身份 grantConsume/kms:Decrypt 必须同时被 DataKey 的资源策略允许。本轮 CloudTrail 证实旧策略仅允许该 Worker 经 Secrets Manager 解密，不能消费专用 SQS。已按[精确修复方案](../audit/QA-09-Command队列解密精确修复方案-2026-10-03.md)添加 CommandQueueConsumerDecrypt：仅指定角色、ViaSQS、唯一队列加密上下文；immediate 开启才应用，原全部策略/CA Secret版本保持。不要将Worker追加到宽泛应用数据面列表。回滚仅移除该Sid并保留Key/队列/消息，分钟补偿继续，不能宣称3秒SLO已通过。

当前失败保留：Telemetry 12/20可见、8超时，完整P95不能成立；MQTT quick 950唯一PROCESSED，但归档积压失败（每分钟默认50批量低于quick正常约60/分钟，另有300突发）。Command首次P95 58180ms失败；精确Key修复后的专项回执独立保存。下一步先修复控制台同小时跨站点择行与归档排空预算，并补Prisma异常回滚/峰值与完整自然生命周期、写权限、117语义场景；不能把部署通过作为完整QA-09 PASS。

复验工具：QA09_EXPECTED_COMMIT/QA09_DEPLOY_RUN_ID显式绑定成功提交与部署Run；版本采集器可选QA09_CODE_RANGE_TRANSPORT=sdk，保留固定VersionId/Range/重组哈希约束。SLO驱动QA09_RUN_MQTT_QUICK=true执行既有610秒quick计划；QA09_COMMAND_ONLY=true仅新测20条在线Command，Telemetry明确NOT_RUN_COMMAND_ONLY。两个模式都写执行源字节、独有prefix、清理/失败回执。不得使用专项NOT_RUN替换先前完整Telemetry FAIL。
