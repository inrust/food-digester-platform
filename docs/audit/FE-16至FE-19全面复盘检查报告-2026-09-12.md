## 一、任务完成概况

### 1.1 总体结论

FE-16～FE-18 已有较完整的页面组件、状态逻辑、REST adapter 和 jsdom 测试，FE-19 也已有顶层 i18n Provider、语言切换器、持久化、62 对语言资源和部分共享组件迁移。然而：

1. `/settings`、`/contracts`、`/contracts/new`、`/contracts/detail`、`/consumables` 虽已登记路由，`AdminWebApp` 却没有对应 controller 或显式页面分支，访问时统一落入“该页面尚未接入当前管理后台组合根”的占位页；生产 bundle 中五个页面 testid 全部不存在。
2. 交付清单及交付 Gate 明确固定在 `FE-01..FE-15`，因此上述缺失存在时 `check:admin-web-delivery` 仍报告 PASS，形成假绿。
3. FE-19 只迁移壳层及 7 个共享文件；开发文档也明确承认 24 个页面仍为中文硬编码。本次全量负向扫描在 64 个非资源 TypeScript/TSX 文件中发现 1,627 行中文硬编码，语言资源不可能覆盖“全部页面”。
4. 现有 Playwright 10 项只覆盖 FE-01～FE-15；没有 FE-16～FE-19 的真实浏览器业务路径、双语言全页或布局断言。
5. 全仓 `pnpm verify` 在 `format:check` 阶段失败，20 个文件不符合格式规范，其中 FE-16～FE-19 相关源码/测试占多数。

按任务清单的任务级完成定义及每项验收基准，四项均判定为 **FAIL / NOT ACCEPTED**，严格实际完成率为 **0/4（0%）**。

### 1.2 完成率口径

本报告不以文件存在、代码行数、组件测试或构建成功折算任务完成。任务只有同时满足以下条件才计为 PASS：

1. 核心功能、功能边界、冻结决策和正式 REST 契约一致；
2. 页面与 API adapter 已接入真实 controller 和浏览器组合根，正式路由可完成业务闭环；
3. lint、format、typecheck、构建、相关单元/契约测试全部通过；
4. 验收基准中的权限、敏感数据、409、状态机、时区、双语言和响应式边界有确定性测试；
5. 核心路径由真实 Chromium E2E 证明，而不是只渲染孤立组件；
6. 如声明目标环境完成，必须另有绑定精确源码提交、真实 Cognito 与已部署 API 的回执。

计算公式：`严格实际完成率 = PASS 任务数 / 4 × 100%`。`CONDITIONAL`、`FAIL` 和 `NOT RUN` 均不计入完成数。

### 2.2 需求、规范和验收逐项核对

#### FE-16

- 平台用户邀请、已有角色分配、Customer scope、停用和触发重置均有 API adapter；邀请类型和请求体不含永久密码，角色/停用/重置使用明确确认。
- RBAC 权限矩阵使用 disabled 复选框，只允许分配固定角色；PlatformOperator 的界面名使用“设备操作员”。
- 业务设置 key 集与 OpenAPI 一致，`command.confirmation` 只读，其他更新携 `version`，409 可显示刷新入口。
- 任务要求设备用户按 Region/Subregion/Device 筛选；当前 `listDeviceUsers` 与 FE-09 页面只有 customerId/status/keyword。开发文档已把它列为未决契约差距，不能计为完成。
- 设置值编辑器只验证能否 `JSON.parse`，没有按各设置 key 的 Schema 做前端字段级校验；非法配置需完全依赖后端 400。
- `/settings` 路由虽允许 PlatformSuperAdmin/CustomerAdmin，但组合根没有 `settings` 分支，用户只能看到占位页。

#### FE-17

- 三个页面组件覆盖列表、详情、续约、终止、关联/解绑、关联历史、四轴状态及 License 独立显示；写 API adapter 均携 If-Match/version。
- Customer 和 eligible 设备来自结构化选项，未提供自由文本地域或任意 deviceId 输入。
- 新建页先调用 `createContract` 创建 DRAFT，之后才列出 eligible 设备；“完成”按钮始终可点击。用户可创建零设备 Contract 并直接完成，与验收基准“无设备有明确字段错误”不符。现有测试只验证绑定按钮在零选择时禁用，没有验证“完成”被阻止。
- `/contracts/new` 的路由守卫允许 PlatformOperator/Auditor，与父列表读权限相同；新建页面本身不接收 role/canWrite，若接线后只读角色可进入完整表单并发起 POST，最终只能依赖后端 403。该行为不符合按角色隐藏/禁用写操作的共同规范。
- `/contracts`、`/contracts/new`、`/contracts/detail` 均无 controller 和组合根分支，当前不存在真实列表加载、N+1 设备计数、详情回源、写后刷新或 409 恢复闭环。

#### FE-18

- 页面组件覆盖 Region/Subregion/Site、连接、关键字、阈值和类型筛选；`unknown` 不绘制进度条，`stale` 明确标记。
- 申请状态矩阵为 Pending→Processing→Completed/Cancelled，写操作携 version；组件测试覆盖非法跳级、409、幂等 replay 和 in-flight 防双击。
- 联系方式不是点击后请求：列表响应已为每条记录携带 `contact`，按钮只控制是否把已在内存/网络响应中的号码显示到 DOM。无权限角色的 `contact=null` 能防止越权显示，但有权限角色在未点击时已批量下载全部号码，不满足“点击后按权限加载”的数据最小化要求。
- 10/30 阈值虽可由 props 覆盖，但当前没有 controller 从 `dictionary.displayNames` 或业务设置加载；默认常量仍是实际唯一来源。
- `/consumables` 没有 controller/组合根分支，因此实际列表、申请队列、阈值配置、联系人权限和状态操作均不可达。

#### FE-19

- `I18nProvider` 已在应用顶层挂载；顶部栏语言切换即时更新，localStorage 能跨刷新/重新挂载保持，`html.lang` 同步。
- en/zh-CN 各有 62 个 key，当前 key 集一致且非空；统一错误映射和日期区域格式化有测试，requestId 保持原文。
- 语言资源仅覆盖通用文案、菜单和错误；业务页面没有调用 `useI18n`。FE-16 页面本身有 92 行中文硬编码，FE-17 四个主要文件有 144 行，FE-18 两个主要文件有 88 行；全前端负向扫描为 64 个文件、1,627 行。
- 所谓“硬编码检测为 0”只遍历 Topbar、Sidebar、breadcrumb、ErrorNotice、ConfirmDialog、CursorTable、TimeText 7 个已迁移文件，并不扫描任务要求的全部页面，不能作为 FE-19 验收证据。
- 目前只验证日期的 locale；没有业务数字、百分比和单位随 locale 格式化的覆盖，也没有英文/中文在 375/768/1440px 下无截断/溢出的视觉或几何断言。

### 3.6 风险归纳

1. **交付风险最高**：菜单/路由存在但页面不可达，用户得到占位页；生产 bundle 也证明页面代码未进入可执行路径。
2. **Gate 可信度风险高**：组件测试、构建、现有 delivery Gate 和现有 Playwright 都可全绿，却系统性排除了 FE-16～19。
3. **权限与隐私风险高**：FE-17 的只读角色写入口和 FE-18 的联系人批量预载均需要在组合前先修正。
4. **国际化缺口是主体未完成而非尾项**：当前资源与检测只覆盖壳层，不能将框架落地等同于双语言任务完成。
5. **证据边界仍未闭合**：当前没有本次任务的目标环境回执；即使本地缺陷关闭，目标层仍须保持 `NOT RUN / NO RECEIPT`。

## 四、整改建议

### 4.1 P0：先恢复真实交付和失败关闭

1. 为 FE-16～18 实现 controllers：负责首屏数据、筛选、游标/刷新、详情、写操作、409 回源、角色、Customer scope、拓扑选项和业务设置注入。
2. 在 `AdminWebApp` 为 `settings`、`contract-modify`、`contract-new`、`contract-detail`、`device-consumable` 增加显式分支，并纳入 `IMPLEMENTED_PAGE_STATES`；构建后断言五个页面 testid 存在。
3. 将交付 manifest 和 Gate 升级到 FE-01～FE-19，登记五个路由、controllers、稳定 testid 及 FE-16～18 的全部 OpenAPI operationId；添加删除任一任务/route/controller/testid/operation 即失败的负向测试。
4. 完成全部页面 i18n 迁移：组件不得硬编码中英文 UI 文案；扩充 en/zh-CN 资源；扫描范围应从 7 文件改为全量 UI 源码，并对允许保留的协议枚举/业务数据建立窄白名单。
5. 运行 Prettier 修复当前 20 个文件，并在不修改业务行为的前提下恢复 `pnpm verify` 全绿。

### 4.2 P1：关闭权限、业务和隐私缺陷

1. FE-16 先演进 Device User 查询契约以支持 Region/Subregion/Device，或由 controller 使用权威 Site/Device 数据源做可证明的完整筛选；不要用当前页数据派生假全量选项。
2. 为四类业务设置建立版本化 JSON Schema，前后端共享校验；前端给出字段路径、范围和类型错误，后端仍作最终裁决。
3. FE-17 在创建事务前选择至少一台 eligible 设备，或在第二阶段完成前禁止离开/“完成”并提供明确错误及可恢复草稿语义；补零设备负向 E2E。
4. 将 `/contracts/new` 守卫限制到 `contract:write` 角色，或让页面接收真实权限并完全禁用/隐藏写表单；仍保留后端 403 纵深防御。
5. FE-18 新增按设备/记录 ID 的联系人按需端点，点击后再发起授权请求；列表响应不得携号码。保留 403/404、跨 Customer 和 DOM/网络/日志零泄露测试。
