## 已核对事实与不能补证的部分

[只读诊断回执](evidence/qa-09-performance-readonly-diagnostic-2026-10-03.json)记录当前 Admin API `ldark4ozek/test` 没有 accessLogSettings、methodSettings 或 tracing，execution log group也不存在。四个旧HTTP500请求ID逐个检索Lambda日志，检索结果/分页完整性分别保存。没有Gateway integration日志，不能把零Lambda匹配解释为请求没有发出，也不能将同分钟两次Throttles推定为逐请求根因。

当前19个函数中18个数据库型函数的预留并发合计31；Admin API=8，Device API=6，Onboarding API=2，15个数据库后台各1。Archive为第19个函数，源码仅调用S3、当前无DB_SECRET_ARN，原并发查询空响应被记录为解析错误；它不纳入数据库pool预算，不能把缺失预留并发当成0数据库压力。数据库poolMax=2，理论稳态62连接。RDS为db.t4g.micro/PostgreSQL16.13。前轮76仅扣了superuser保留，现已纠正：[本轮READ ONLY实测](evidence/qa-09-performance-capacity-readonly-2026-10-03.json) max_connections=79、superuser_reserved_connections=3、reserved_connections=2、rds.rds_reserved_connections=4。规划按不占用三类保留的70条连接预算（79−3−2−4），不依赖应用账号是否获得特殊保留槽权限。实测client backend为14（含诊断1），CloudWatch本轮峰值27；这不证明轮换峰值安全。PG16保留语义见[PostgreSQL文档](https://www.postgresql.org/docs/16/runtime-config-connection.html)，RDS16.5起新增rds_reserved角色/独立参数见[AWS发布说明](https://docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-versions.html)。应用账号角色及RDS实际准入行为仍应在不耗尽连接的方式下核验，不使用76作为普通应用容量。

Reserved Concurrency用于限制下游压力，但不能把它当作存活连接的硬上限：冷/热执行环境轮换、闲置连接、重试、诊断与迁移都占预算。AWS说明见[Reserved concurrency](https://docs.aws.amazon.com/lambda/latest/dg/configuration-concurrency.html)和[Concurrency scaling](https://docs.aws.amazon.com/lambda/latest/dg/lambda-concurrency.html)。本轮不直接将8改为10/12。

## 最小可观测性修复

建议先部署独立Admin API access日志，不启用请求/响应body logging。字段限定：requestId、extendedRequestId、requestTimeEpoch、resourcePath模板、httpMethod、status、integration.status、integration.integrationStatus、integration.requestId、integration.latency、responseLatency及error.responseType（标准类别）。不得记录Authorization、Cookie、queryString、body、JWT、凭据或签名URL。具体REST字段依[AWS日志变量文档](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-variables-for-access-logging.html)验证，不能套用HTTP API不存在字段。

只读`get-account`确认区域cloudWatchRoleArn也为空；部署前须明确审批新增区域API Gateway日志Role及窄授权，不能默认仅Stage修改即可。字段模板见[待实施配置](evidence/qa-09-admin-access-log-proposal-2026-10-03.json)。access日志TTL建议7天、KMS/读取权限收敛现有运维角色，保留是否截断/缺失证明。仅错误类别做聚合；首版不记录integrationErrorMessage/free-form errorMessage，避免自由异常文本泄露；以integrationStatus及标准error.responseType判定类别。字段缺失时如实标记关联不足，不扩大记录范围。Lambda入口记录Gateway requestId与Lambda awsRequestId及operationId/status/elapsedMs，禁止正文和身份Token。客户端保留两个Gateway响应请求ID及单调计时。拿同一requestId的Gateway status500、integrationStatus429/TooManyRequests和Lambda指标确认请求级根因；被拒绝调用本来可能没有Lambda START日志，不把START缺失当成独立证明。

Gate：10客户端无重试真实突发，全部请求均有可核对access行，故障请求分类明确；日志扫描零凭据泄露。部署失败回退前一CDK版本；日志新增与并发扩容分两步，避免同时改变根因。日志/共享IAM调整需要另行授权，当前未实施。

## 连接预算约束与候选容量

容量算式：`sum(reservedConcurrency × poolMax) + operationalReserve + idleOverlapReserve <= ordinarySlots`。规划暂取运维/诊断8、轮换重叠10，须依据真实pg_stat_activity/环境轮换实测扩大，不降低预算以过Gate。

| 候选 | 稳态连接 | 加18条保留后的需求 | 对70保守预算判断 |
| --- | ---: | ---: | --- |
| 当前Admin8/pool2，其他23/pool2 | 62 | 80 | 完整预算不满足；超10条，当前稳态算式不代表安全峰值 |
| 直接Admin12/pool2 | 70 | 88 | 拒绝，超18条 |
| 仅Admin12/pool1，其他23/pool2 | 58 | 76 | 拒绝，仍超6条；纠正前轮候选结论 |
| Admin12/pool1、Device6/pool2、Onboarding2/pool2、15Worker各1/pool1 | 43 | 61 | 算术余量9条；需全部相关Worker串行/事务/延迟及轮换压力证明 |

候选必须支持按函数区分pool配置，同时验证Admin与Worker pool1的SQL串行影响；console使用并行域查询，缩池可能使P95变差。先本地真实PostgreSQL并发与事务/死锁测试，再在已授权测试部署后取数据库连接峰值和API500/P95。如普通槽位或重叠预算不满足，应准备RDS规格扩大或RDS Proxy方案及成本，不盲目调Lambda并发。Proxy是否适用还需检查会话钉扎、事务和Secret轮换。备选是保持8并发并明确过载503/Retry-After，但这不能冒充原10客户端无错误容量验收。

验收同时要求：HTTP实际300请求/10并发、无500/重试掩盖；连接峰值低于普通槽位减运维保留、重叠测量不超预算；Telemetry API可见P95≤5秒、在线Command实际Broker收到P95≤3秒；并发期间Worker队列可排空。预算纯函数负向测试见`scripts/qa09-capacity-budget.test.mjs`，它不替代真实容量Gate。

## MQTT与Command后续修复边界

修正发布器先以真实publish-attempt时间/PUBACK账本复验300条/10秒突发，再核对950唯一消息及920条Telemetry归档原文一致。PUBACK不能证明业务入库或API可见。API可见测量用同一客户端单调时钟与唯一递增指标max，发布前确认marker未出现；轮询间隔250ms是检测上界，不扣除API调用耗时。

Command Publisher的当前CDK为每分钟schedule，必须测API发起到已订阅在线设备收到指定meta.id；只读代码事实不足以报P95。若实测超过3秒，候选为Command AUTHORIZED持久化后经Outbox/SQS触发发布，原1分钟扫描保留故障补偿。API事务提交与投递失败须可恢复、meta.id幂等、再次租约抢占安全；不能在API响应前无事务保障地直接Publish。该应用改动与部署没有自动包含在本轮验收授权中。

仅本轮队列重投允许精确重新提交已PROCESSED消息的原文摘要与本轮证书ID，不能ReceiveMessage消费共享队列、Purge队列或调整visibility/concurrency。SendMessage成功只是已提交，缺消费级关联时不得标PASS。

### Command候选事件路径与预算

不能只增加一个仍由每分钟Outbox扫描器启动的分支。候选路径为：API事务同时持久化命令及`COMMAND_PUBLISH_REQUESTED` Outbox；提交后立即向专用SQS发送commandId指针；消费Worker用原幂等租约抢占并真实MQTT发布，随后更新状态。发送失败保留Outbox，由旧分钟扫描补偿；补偿不冒充正常3秒SLO。禁止无事务持久化就先Publish。使用batchSize1/maxBatchingWindow0，评估Publisher预留并发2（SQS与补偿共享上限、并发抢占安全）及冷启动耗时；在联合pool1候选上增加1条连接，需求从61变62、规划余量8。正常/重复/发送失败/超时与到达ACK均须同一commandId证明。尚未增加队列、改IAM/Worker/事件源或部署。
