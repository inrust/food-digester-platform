### 3.5 风险总览

1. **交付风险最高**：源码已写但未进入组合根，真实用户无法使用；这是五项任务全部 FAIL 的直接原因。
2. **Gate 可信度风险**：`pnpm verify` 全绿仍遗漏整个任务族，说明现有清单驱动 Gate 不能证明“应交付集合完整”。
3. **业务闭环风险**：Media 内容、设备历史、退役确认、历史 License、Device User 同步状态均存在数据契约或页面闭环缺口。
4. **安全与租户风险未实证**：组件层能呈现 403/404，不等于部署后的 Cognito 角色、Customer scope 和跨租户拒绝已通过。
5. **目标环境风险**：无精确提交绑定的部署、请求/响应和清理回执，任何本地 PASS 均不能提升目标环境状态。

## 四、整改建议

### 4.1 P0：先恢复可运行交付与失败关闭 Gate

1. 为 `device-view`、`device-manage`、`licenses`、`configurations`、`device-users`、`alarms` 实现 controller；在 controller 中统一完成初始加载、刷新、游标、详情、写操作、错误和 Session/Customer scope 注入。
2. 在 `AdminWebApp` 为六个 pageState 增加显式渲染分支，移除本次范围页面落入默认占位的可能。
3. 更新 `admin-web-delivery-manifest.json`，登记六个路由及实际使用的全部 OpenAPI operationId。
4. 改造交付 Gate：以版本化“已交付任务/路由/operation”事实表为源，与 `APP_ROUTES`、组合根、OpenAPI 和浏览器产物双向比对；新增负向测试，删除任一 FE-06～10 路由/controller/operation 时必须失败。
5. 为六个路由新增真实 Chromium E2E，至少覆盖五角色可见性、成功/空/错/403/404/409、重复提交、Customer scope、分页、设备切换、时区、焦点和 1440/768/375px。

### 4.2 P1：补齐业务闭环

1. `FE-06`：接入 BE-MED-01 的短期下载 URL并渲染最新授权对象；接入 BE-DEV-05 activities 作为历史视图；筛选选项改用 Site/Customer 权威数据源。
2. `FE-07`：为退役记录建立可查询契约，或把足以恢复 `PENDING_CONFIRMATION`/完成状态的字段加入设备详情；在页面刷新后重新取得真实状态。Alias 校验复用 DEC-019 策略实现 code point 计数、trim/NFC 和提示。
3. `FE-08`：新增正式 License 列表/搜索 API，支持历史终态档案枚举；FE-17 落地后完成 Contract 详情中的独立摘要与跳转；按规格只渲染合法动作。
4. `FE-09`：为 USERS_CHANGED 增加可查询的投递/设备同步状态，明确区分“实体版本”“通知已发布”“设备已领取/应用”。
5. `FE-10`：使用结构化 Customer/Site/Device 选择器；由浏览器路由 controller 双向同步 URL 和页面 state；为 Critical 增加真实视觉样式与浏览器断言。

### 4.3 P2：修正文档与证据治理

1. 将五份 `docs/dev/FE-*` 改为 `module present / app integrated / browser verified / target integrated` 四层状态，删除在组合根未接入时的任务级 ✅。
2. 将已知缺口转为可追踪问题 ID、owner、关闭条件和验证命令，避免只写“待后续集成”。
3. 目标环境验收必须绑定修复后的精确源码提交，保存真实 Cognito 角色、部署后 Admin API、跨 Customer 拒绝、并发冲突、敏感字段零泄露和清理回执；回执缺失时保持 `NOT RUN / NO RECEIPT`。
