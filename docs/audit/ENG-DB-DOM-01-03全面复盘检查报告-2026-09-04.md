### 1.2 判定口径

本报告采用严格完成口径：任务只有在核心内容、技术对接要求、交付物和全部验收基准均满足，且不存在会推翻该任务验收结论的打开问题时，才计为“完成”。“代码或文档已存在”“现有测试通过”“全仓 `pnpm verify` 退出 0”均不能单独替代任务验收。

问题等级定义：

- **阻塞级**：当前无法继续验收或会导致系统不可启动、不可迁移、不可恢复；
- **高危**：可能造成跨 Customer 数据污染、并发业务约束失效、敏感材料泄露，或使关键质量 Gate 产生错误通过；
- **中危**：重要规范/验收覆盖缺失，通常不会立即破坏全部系统，但会显著扩大缺陷进入主干的概率；
- **低危**：文档、证据或维护性偏差，对当前运行影响有限。

### 3.5 关联风险说明

- H-01、M-01 和 M-02 属于“门禁错误通过”：修复业务代码前，应先修复 Gate 并加入本报告的负向样本，避免整改后回归。
- H-02、H-03 和 H-04 共同影响 Customer/License 数据完整性。只修应用层预检不能关闭风险，必须有数据库约束与并发测试兜底。
- H-05 与 M-05 共同影响审计可信度：前者可能泄密，后者造成关键上下文缺失。审计服务不能在关闭这两项前宣告满足 DOM-03。
- DOM-01 的纯领域状态机通过验收，但 M-04 会削弱其持久化消费者；该问题关闭责任应由 DB-01/DOM-01 集成共同承担，不能通过删掉 `axis` 来迁就旧表。

## 4. 整改建议

### 4.1 P0：关闭高危问题并让 Gate 先失败、后通过

1. **重写 Migration 漂移检查（H-01）**：使用 Prisma/PostgreSQL 可执行 diff，把“全部 Migration 应用后的 Schema”与 `schema.prisma` 期望结构比较；增加“已有旧 Migration + Schema 新增字段/模型但未新增 Migration”的负向测试。
2. **补齐租户和归属约束（H-02）**：为 Customer 业务表明确直接 tenant key 或受控父链；对 Device↔Site↔Customer、Assignment、ContractDevice、License 等建立外键/复合外键或约束触发器；加入孤儿 Customer、跨 Customer Site/Device、跨 Customer Contract/License 的 PGlite 负向测试。
3. **统一有效 License 集合（H-03）**：将 `Renewed` 纳入数据库部分唯一索引，或通过正式决策把它移出领域“有效”集合；同步 Prisma 注释、Migration、服务阻断集合、领域函数和并发测试。
4. **冻结 Repository 保留字段（H-04）**：`updateWithVersion` 明确剔除/拒绝 `id/customerId/version/deletedAt` 等保留字段，成功后按原 scope 读取；增加“尝试改写 customerId 必须失败且原记录不变”的集成测试。
5. **升级审计脱敏（H-05）**：字段名规则之外增加 PEM、JWT、常见 Token/密钥值形态检测；对二进制、Date、Decimal、BigInt 和循环对象定义确定处理策略；增加非标准键名下私钥的 0 泄露测试。

### 4.2 P1：补齐验收覆盖和领域边界

1. 使用 Ajv 2020 或等价实现对全部 JSON Schema 执行元 Schema 语义验证，并把非法关键字/非法 `type` 加入 M-01 负向测试。
2. 扩大敏感信息扫描输入集，至少覆盖 tracked、staged 和未忽略的 untracked 文本文件；为大文件/二进制例外保留显式日志和规则测试。
3. 将 `renewLicense` 的 actor 校验放到所有分支之前；幂等重放不应产生新的 history/notification descriptor，或应返回独立 replay result 类型。
4. 为 `device_state_history` 新增 `axis` 封闭枚举及 Migration，所有写入消费者必须持久化 `effects.stateHistory[].axis`，并补 Lifecycle/Operational 同名状态查询测试。
5. 扩展请求上下文和 `AuditedOperation`，由可信 HTTP 适配层注入规范化 IP/User-Agent；禁止从业务请求 body 取值，并验证成功/失败两条路径均记录。
6. 将 Node 支持范围改为与工具链一致的范围（建议显式 `>=20.19 <21`，或正式支持并验证 Node 22/24）；在自动化环境用 Node 20.19+ 执行一次无缓存 `install/lint/typecheck/test/build`。

### 4.3 P2：证据与文档维护

1. 更新 ENG-01/02、DB-01/02、DOM-01/02/03 开发文档中的测试数量和风险说明；避免把易漂移总数写成永久结论。
2. 修复完成后运行当前工作树与隔离干净副本两轮 `pnpm verify`，报告分别记录 Node/pnpm 版本、缓存状态、测试计数和退出码。
3. 对 12 个问题逐项建立回归测试；只有问题关闭且复验通过后，才提升对应任务状态与严格完成率。
