# Onboarding 首次申请去库存前置修复（2026-10-18）

用户明确纠正业务流程：设备首先提交申请，系统只按序列号判断是否曾提交；从未提交则创建待审核申请，已提交则提示无需重复提交，不要求提前登记库存。原库存前置校验使未入库的真实设备收到业务 404，是本次修复的问题。

## 当前行为

- `POST /api/v1/device/onboarding/request` 保留字段/CSR 校验、IP 与序列号限流；不查询或创建设备、不提前绑定公钥。首次返回 `201 {requestId,status:PENDING}`。
- 同序列号已有任意状态申请（PENDING / APPROVED / REJECTED / TIMED_OUT），无论 CSR 是否相同，返回 `409 CONFLICT` 和已提交提示。数据库全状态唯一索引防止并发重复；不覆盖旧资料，不把原申请 ID 暴露给重复提交者。错误中的 requestId 是 HTTP 追踪 ID。
- 管理员批准时，在现有审计事务内创建设备台账、绑定公钥、迁移状态、写状态历史与 Provisioning Job；公钥被其他设备占用时全部回滚并记 FAILURE 审计。拒绝无台账申请只保存拒绝结果与原因。兼容已有 PendingOnboarding 台账的资料和状态校验。
- 拒绝或超时仍属于已提交，不能再次申请；异常须人工核查，本次没有新增重置或恢复接口。证书包恢复、首 Heartbeat、签名轮询及证书轮换规则继续使用各自既有实现。

当前契约版本 `0.14.0`，决策登记 `1.37.0`；DEC-025@1.2.0、DEC-017@1.1.0、DEC-026@1.1.0 记录本次业务授权。新旧契约 wire 比较明确批准移除申请接口的 200 / 库存 404。旧 0.11 / 0.12 / 0.13 基线及审批映射不改写；旧映射使用从基线提交原样封存的 1.36.0 决策登记复验。

## 部署前置与回滚边界

本次未读取或更改目标数据库。部署前先在目标数据库只读检查：

```sql
SELECT serial_number, COUNT(*) AS request_count
FROM onboarding_requests
GROUP BY serial_number
HAVING COUNT(*) > 1;
```

新迁移 `20261018090000_onboarding_request_serial_unique` 在事务内创建全状态唯一索引，再删除旧 PENDING 部分唯一索引。若存在历史重复申请，迁移会失败，不会自动删除或改写历史记录；须先由运维审查重复历史并制定保留方案。迁移成功后再发布 request 和 admin 审批运行时，随后用一个未提交过的实物序列号验证首次 201、重复 409 和审批发证。

不能直接把旧审批代码回滚到存在无台账 PENDING 新申请的环境：旧实现无法审批这些申请。回滚前须处理或保留这些新申请的可审核路径；不得以删除申请或强制改生命周期代替处置。旧唯一索引的恢复与新索引撤销也须单独审核，不由应用代码自动执行。
