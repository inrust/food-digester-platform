| 乱序允许窗口内重算 | 部分符合 | receivedAt 窗口内迟到可收敛；不满足 event-time 窗口，且没有生产入口定义允许窗口 |

## 3. 问题清单及风险分析

### 3.1 汇总

| 严重度 | 数量 | 主要影响 |
|---|---:|---|
| 阻塞级 | 3 | Archive/Summary 实际执行 501；Replay API/Worker 不可达 |
| 高危 | 5 | 重复归档、静默丢档、事件时间错误、租户/站点聚合错误、Replay 中断后永久卡死 |
| 中危 | 8 | Publisher 职责混用、并发领取、完整率误报、非原子 upsert/审计、统计失败语义、Gate 假绿、缺云证据 |
| 低危 | 1 | 任务文档链接和历史证据失真 |
| 合计 | **17** | 当前四项整体不可验收 |

### 3.2 阻塞级

#### B-01 Archive Lambda 仍是内联 501 占位实现

- **所属模块**：BE-ARC-02 / infra / archive-worker
- **具体表现**：`ArchiveFn` 调用 `mkFunction` 时未提供 entry；`mkFunction` 因此部署 `PLACEHOLDER_HANDLER_CODE`。`apps/archive-worker` 也仍只导出 ENG 骨架。
- **影响范围**：全部 Archive SQS 消息。即使 BE-ARC-01 成功发送，生产 Lambda 也不会执行 NDJSON/GZIP、S3 写入或 Manifest。
- **风险**：原始 Telemetry/Report/Alarm/Event/Tamper、License/OTA 记录全部无法归档，BE-ARC-02 及依赖它的 Replay 不可发布。

#### B-02 Summary Lambda 仍是内联 501 占位实现

- **所属模块**：BE-ESG-01 / infra / summary-worker
- **具体表现**：`SummaryFn` 有每小时 EventBridge 调度，却没有 entry；每次调度命中 501 占位 Handler。`apps/summary-worker` 仍是 ENG 骨架。
- **影响范围**：telemetry_daily、ESG daily summary、完整率补齐和计算版本更新。
- **风险**：生产汇总不生成，下游 Dashboard/ESG API 读取陈旧或空数据。

#### B-03 Replay API 和 Worker 均未进入生产组合根

- **所属模块**：BE-RPL-01 / cloud-api runtime / infra / aws-clients
- **具体表现**：Admin Lambda 只实例化 Onboarding 与 CertificateRotation；路由事实表不含 create/list/get Replay operation，实际请求返回 404。CDK 没有 Replay Lambda/队列/调度；仓库也没有 S3 Reader、Ingress SQS Sink 或 iotPrincipal 注入适配器。
- **影响范围**：Replay Job 创建、查询、执行全链；OpenAPI 中三个接口只是不可达契约。
- **风险**：运维无法发起重放，已有库级 Worker 无生产调用者；BE-RPL-01 交付物不成立。

### 3.3 高危

#### H-01 归档去重只对批内和完全相同批次有效

- **所属模块**：BE-ARC-01/02 / Archive Worker
- **具体表现**：part key 取决于当前批次 eventId 集合。第一次 `[A,B]`、重试/重复投递 `[A]` 会得到不同 key；A 同时出现在两个 S3 对象。现有测试只覆盖批内重复和“相同批次原样重跑”。
- **影响范围**：Lambda partial retry、批窗口变化、并发 Publisher、发送后中断产生的所有重复投递。
- **风险**：审计、Athena/离线处理和 Replay 均可能重复消费同一原始事件；BE-ARC-01“发送后中断不产生重复归档对象记录”验收失败。

#### H-02 强制归档记录校验失败会被静默 skipped

- **所属模块**：BE-ARC-02 / Archive Worker
- **具体表现**：缺 customerId、版本错误、类型混用或未知字段映射失败时只增加 `skipped` 并继续；没有抛错、Quarantine、DLQ/partial batch failure 标记或持久化拒绝原因。
- **影响范围**：Telemetry/Report/Alarm/Event/Tamper 与 License/OTA 归档载荷漂移或局部损坏。
- **风险**：消息可能被 SQS 确认后永久丢档，违反“必须归档”和审计可追溯要求。

#### H-03 Telemetry 完整率使用 received time 而非 event time

- **所属模块**：BE-ESG-01 / IngestionReceipt / Aggregation Worker
- **具体表现**：receipt 无 occurredAt；Worker 按 receivedAt 的小时/日期分桶。开发文档把它称为“近似”，但任务核心明确要求 event time。
- **影响范围**：离线补报、网络拥塞、Replay、跨小时/日迟到数据。
- **风险**：完整率与日汇总落到错误业务期间，不能作为 ESG 数据质量依据。

#### H-04 Customer/Site 维度缺失且设备归属变化可使聚合失败

- **所属模块**：BE-ESG-01 / Database / Aggregation Worker
- **具体表现**：daily/esg 只按 device+day 分组，以第一行 customerId 写结果；没有 siteId。负向探针在同设备同日先属于 Customer A、后属于 B 时，Worker 合并两行并用 A 写入，数据库当前归属校验触发 `device/customer mismatch`，整次运行失败。
- **影响范围**：设备重分配 Customer/Site 的当天及其同批其他设备；历史 Site 归属查询。
- **风险**：跨租户错误归集或整批停更；不满足 Customer/Site 生成要求。

#### H-05 Replay Job 领取后中断会永久停在 RUNNING

- **所属模块**：BE-RPL-01 / Replay Worker / replay_jobs
- **具体表现**：PENDING 条件更新为 RUNNING 后没有 lease、startedAt、heartbeat、attempt 或恢复扫描；后续调用对任何非 PENDING 直接返回 ALREADY_DONE。
- **影响范围**：S3 扫描、解压、逐条发送、终态写入之前任一点的进程崩溃或 Lambda 超时。
- **风险**：任务永久卡死、可能已部分重投且无最终统计/审计；需要人工数据库修复才能恢复。

### 3.4 中危

#### M-01 BE-ARC-01 生产 Publisher 混合消费 Notification

- **所属模块**：BE-ARC-01 / Outbox Publisher runtime
- **具体表现**：生产 entry 注入 notificationSender，查询条件扩展为 ARCHIVE + Notification Catalog，且拥有 IoT Publish 权限。
- **影响范围**：Archive 与设备通知共享 batchSize、调度和失败域；通知积压可能延迟归档。
- **风险**：违反“仅领取 ARCHIVE，其他事件由各自发布器处理”的明确职责边界。

#### M-02 Outbox 并发领取与 retryCount 更新并非原子

- **所属模块**：BE-ARC-01 / Outbox Publisher
- **具体表现**：先无锁 `findMany` 再发送；多个实例可同时领取同一行。失败更新把 `row.retryCount + 1` 的旧值写回，而不是数据库原子增量。
- **影响范围**：EventBridge 重叠执行、手工并发调用、慢 SQS/DB 时段。
- **风险**：重复发送放大 H-01，retryCount 少计，claimed/published 指标失真。

#### M-03 完整率边界缺口误报且 Telemetry 缺失数未持久化

- **所属模块**：BE-ESG-01 / Aggregation Worker / telemetry_hourly/daily
- **具体表现**：完整率只用窗口内 min/max；`[2,3]` 返回 100%/missing=0，无法识别 seq=1 边界缺口。函数虽计算 missing，但两张 Telemetry 表无 missingRecordCount，写入时直接丢弃。
- **影响范围**：窗口首尾缺口、日切、设备重启/序号重置、管理端完整率展示。
- **风险**：数据质量被高估，不满足“缺失序号正确反映完整率”和“计算缺失数”。

#### M-04 Aggregation 的“upsert”只保证顺序幂等

- **所属模块**：BE-ESG-01 / Aggregation Worker
- **具体表现**：daily/esg 使用 findFirst→update/else create；并发 Summary 调用可同时查无记录后撞唯一键，或基于不同快照覆盖。
- **影响范围**：EventBridge 重叠、补算与正常调度并发、手工回填。
- **风险**：任务失败或结果回退；当前“重复执行结果不变”测试只覆盖顺序二次执行。

#### M-05 Replay 终态与执行审计不是一个事务

- **所属模块**：BE-RPL-01 / Replay Worker / DOM-03
- **具体表现**：先 updateMany 写 COMPLETED/FAILED，再独立 `recordAudit`。审计失败时 Job 已是终态，再次执行直接 ALREADY_DONE。
- **影响范围**：所有 Replay 执行的数据库瞬时错误路径。
- **风险**：存在完成/失败 Job 但没有执行审计，违反“每次执行写审计”。

#### M-06 Replay 逐行失败统计不完整

- **所属模块**：BE-RPL-01 / Replay Worker
- **具体表现**：只有 sink.send 位于逐行 try/catch；JSON.parse、解压和读取错误直接令整个任务 FAILED，不计入 failed 行数，也不能继续处理同对象后续合法行。
- **影响范围**：局部损坏 NDJSON、单个坏对象、历史格式漂移。
- **风险**：成功/跳过/失败统计与实际扫描不一致，小范围坏数据阻断整个 Job。

#### M-07 默认 Gate 未覆盖本次任务的生产交付面

- **所属模块**：scripts / CI / infra tests
- **具体表现**：`check:runtime` 只检查六份 Onboarding/Device OpenAPI；`check:cdk` 的 delivered Lambda 列表排除 ArchiveFn/SummaryFn；`app-stack` 的真实 asset 断言同样排除二者；证据 Gate 未纳入本次四份开发文档。
- **影响范围**：CI 和发布评审。
- **风险**：即使生产仍是 501/404，`pnpm verify` 仍输出全绿和“已交付 Lambda 全部使用真实 asset”，造成错误验收信号。

#### M-08 缺少目标 AWS 运行证据

- **所属模块**：BE-ARC-01/02、BE-RPL-01、BE-ESG-01 / 发布验收
- **具体表现**：独立 AWS 数据链路 Gate 因缺少回执退出 1；没有真实 Archive SQS 消费、S3 对象/Manifest、Replay 投递或 Summary 定时执行证据。
- **影响范围**：目标账号中的 IAM、VPC、Secret、SQS、S3、EventBridge 和 Lambda 行为。
- **风险**：本地实现即使修复也不能直接声明云端验收；当前生产占位问题使该证据实际上无法生成。

### 3.5 低危

#### L-01 开发文档存在 10 个失效链接和陈旧结论

- **所属模块**：`docs/dev/BE-ARC-01...`、`docs/dev/BE-RPL-01...`
- **具体表现**：两份文件从 `docs/dev` 使用 `../apps`、`../packages`、`../contracts`，实际解析到不存在的 `docs/apps` 等路径；应使用 `../../...`。文档还保留旧测试总数，并把生产接线错误划到 IAC 边界外。
- **影响范围**：代码审查、验收导航和维护可信度。
- **风险**：不直接改变运行时，但会掩盖“交付物存在”和“生产可用”的差异。

## 4. 整改建议

### 4.1 P0：先解除生产不可用

1. **接通 Archive Worker**：新增真实 SQS Lambda entry，解析 `Records`、调用 `createArchiveWorker`，按 item 返回 partial batch failures；使用 `createS3ArchiveObjectStore`，补充非法强制归档记录的 Quarantine/DLQ 语义；CDK `ArchiveFn` 改为 NodejsFunction asset。
2. **接通 Summary Worker**：新增真实定时 Lambda entry，解析明确的 event-time 重算窗口，连接数据库并调用聚合服务；CDK `SummaryFn` 改为 asset；`apps/summary-worker` 从骨架收敛为唯一生产组合根。
3. **接通 Replay 全链**：把三个 Replay operation 加入 delivered runtime、Admin Lambda 路由和 API Gateway；实现分页 S3 Reader、Ingress SQS Sink、ACTIVE 证书 ARN 注入和 Job 触发队列/Lambda；创建 Job 与触发消息采用事务 outbox，避免 PENDING 永久滞留。
4. **扩展失败关闭 Gate**：把 ArchiveFn、SummaryFn、Replay Worker 纳入 CDK asset Gate；把 `admin-replay-api.json` 纳入 Runtime 双向 Gate；新增断言确保生产路由不是 404、Lambda 不是 ZipFile 501。

### 4.2 P1：修复数据正确性和恢复语义

1. **建立跨批 eventId 幂等**：使用稳定的单事件键/幂等索引、DynamoDB/RDS 去重账本，或在写 part 前查询 Manifest eventId 索引；补充 `[A,B]` 后 `[A]`、partial batch retry、并发批次测试。不要把“Manifest 可追溯”当成已去重。
2. **Archive 失败不可静默成功**：强制来源 Envelope/Schema 错误必须让当前 SQS item retry 或进入专用归档隔离队列，并持久化错误路径、eventId 和原文；heartbeat/media 的策略性跳过与损坏输入必须使用不同结果类型。
3. **按 event time 建模完整率**：为 receipt/聚合输入保存 occurredAt 或直接使用冻结后的事件时间；定义允许迟到窗口、水位线、序号重置和窗口首尾期望范围。
4. **补齐 Customer/Site 历史维度**：聚合输入保存事件发生时的 customerId/siteId，分组键与唯一键包含需要的维度；明确设备重分配切分规则。先加入同日 Customer/Site 变更负向测试。
5. **保存缺失数**：为 telemetry_hourly/daily 增加 missingRecordCount 或等价可查询字段；完整率应结合 ingestion_gaps/期望序号边界，不只使用窗口内 min/max。
6. **使用真正的原子 upsert/事务**：以数据库 `upsert` 或 INSERT ... ON CONFLICT + 版本/锁保证并发幂等；补 Promise.all 并发重算、正常调度与补算竞争测试。
7. **Replay 增加可恢复租约**：记录 startedAt/leaseUntil/attempt/lastHeartbeat，超时 RUNNING 可安全重新领取；依靠原幂等键承受部分重投。Job 终态与 DOM-03 审计应同事务提交。
8. **完善 Replay 逐行容错**：把解压、JSON.parse、Schema/Manifest 校验纳入对象/行级错误计数与隔离策略；继续处理可验证的后续对象，统计中区分 failedObjects/failedLines/sendFailures。

### 4.3 P2：职责、证据与文档收口

1. **拆分 Archive 与 Notification Publisher**：生产 entry 只查询 ARCHIVE；Notification 使用独立 Publisher/调度/指标。若正式决定共用，先变更任务规格并证明无饥饿和失败域耦合。
2. **实现原子领取**：使用 lease 状态或 `FOR UPDATE SKIP LOCKED`，retryCount 使用数据库原子 increment；增加双 Publisher 并发测试。
3. **更新开发文档**：修复 10 个相对链接、任务清单行号和历史测试计数；删除“生产接线归边界外”的错误完成暗示，并将四份文档纳入证据 Gate。
4. **修复后再采集 AWS 实证**：在隔离环境验证 Outbox→Archive SQS→Archive Lambda→S3/Manifest、重复投递、失败隔离、Replay API/Worker、Summary 调度与数据库结果；提交结构化回执后再申请严格验收。

### 4.4 建议复验顺序

1. P0 生产组合根与 Gate；
2. Archive 跨批幂等和失败关闭；
3. ESG event-time、Customer/Site、缺失数和并发；
4. Replay lease、审计原子性和逐行容错；
5. 66 项既有定向回归 + 新增严格负向测试；
6. `pnpm verify`；
7. 隔离 AWS 环境端到端回执；
8. 只有上述全部通过后，才能把严格完成率从 0/4 调整为 4/4。
