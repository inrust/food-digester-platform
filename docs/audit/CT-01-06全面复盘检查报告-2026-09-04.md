### 1.1 判定口径

本次复盘区分三个指标，避免把“文件已存在”误报为“任务已验收”：

1. **交付物存在率**：清单列出的主要文件、类型、测试或矩阵是否存在；
2. **专项要求满足度**：实现和专项测试是否覆盖核心开发内容、技术对接要求与明确验收基准；
3. **严格任务完成率**：单项任务必须同时满足清单 §3、§3.1 和本任务全部验收基准，存在任一未关闭的关键验收缺口即不计为完成。

本报告不以测试数量代替测试有效性。自动检查自身可以产生“假绿”时，即使测试全部通过，相关验收项仍判为未完成。

### 1.2 严重度口径

| 级别 | 判定标准 |
|---|---|
| 阻塞级 | P0 验收基准确定失败，或现有检查会错误放行不可追溯、不可执行的契约 |
| 高危 | 关键覆盖关系无法被证明，后续开发可能遗漏原型能力、权限或接口来源 |
| 中危 | 质量门禁或审计链不完整，当前未发现运行时故障，但无法提供充分验收保证 |
| 低危 | 文档、命名或维护性偏差，短期影响有限但会误导后续开发或审计 |

## 5. 整改建议

### 5.1 P0：关闭 CT-06 阻塞项

1. **建立真实引用集合。**
   - 从全部 `contracts/rest/*-api.json` 自动收集 `operationId`，检查全局唯一；
   - 从管理前端的路由声明生成 `routeId` 清单；尚未实现的路由应进入版本化的 planned-route registry，明确状态和归属任务；
   - 矩阵所有 Adopt/Adapt 引用必须命中真实集合，不能只通过格式正则。

2. **清理 25 个未命中 API 引用。**
   - 对命名漂移项统一采用已发布 OpenAPI operationId；
   - 对尚未落地项建立合法的 OpenAPI 契约桩或明确标记 `Defer`，不得伪装成已可引用的 Adopt/Adapt API；
   - 补充字段级校验：`source.field` 必须存在于对应 operation 的响应或参数 Schema。

3. **让矩阵与原型源双向核对。**
   - 从 `docs/index19.html` 提取菜单、页面、表头、筛选、按钮和模态框的稳定 ID/文本清单；
   - 每个源元素必须恰好映射一个矩阵项，矩阵项也必须能回指源元素；
   - 原型新增、删除、重命名或矩阵漏项均应使检查失败。

4. **补充假绿回归测试。**
   - 不存在的 operationId、routeId、field 必须失败；
   - 删除任一原型元素映射必须失败；
   - 重复映射、孤儿矩阵项和角色越权必须失败。

### 5.2 P1：补齐 CT-05 OpenAPI 标准验证

1. 使用支持 OpenAPI 3.1 的标准验证器校验基座及全部 24 个业务片段；
2. 将基座与片段解析/打包为确定性发布产物，检查跨文件 `$ref`、路径/方法、参数位置、响应、security scheme 和 operationId 全局唯一性；
3. 把完整 OpenAPI 校验纳入 `pnpm verify`，并加入“版本非法、缺少 responses、重复 operationId、非法 parameter/schema”等失败示例；
4. 让 CT-06 直接消费该验证后的 operation registry，避免两套手工命名。

### 5.3 P2：恢复文档一致性

1. 将 `docs/dev/决策登记与契约版本.md` 中 5 个链接的 `../` 修正为 `../../`，并在 CI 增加 Markdown 本地链接检查；
2. 将 CT-06 中 DEC-008 的“暂用”文案更新为正式冻结值及版本；
3. 在本报告之后追加复验记录，不覆盖本次基线结论。
