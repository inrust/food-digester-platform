### 3.5 风险归纳

1. **可用性风险最高**：设备入口和 Ingestion 入口都没有接到已有实现，当前系统无法运行完整流程。
2. **安全与状态一致性风险**：DEC-017 的硬截止依赖定时评估器；迟到 Heartbeat 竞态及 Status 只投影不处置，会造成申请、设备、本地证书记录与 AWS 证书状态分裂。
3. **协议兼容风险**：设备端成功载荷与权威源协议/OpenAPI不一致，属于真实集成缺陷，而非单纯文档问题。
4. **证据失真风险**：模块测试全部通过，但测试固定了旧响应形状，也未覆盖部署组合根和截止竞态；不能用 58/58 或 968/968 推导任务已验收。
5. **发布风险**：全仓 Gate 仍为红色；当前仅能声明若干子检查通过，不能声明 `pnpm verify` 通过。

## 4. 整改建议

### 4.1 P0：先恢复可运行闭环

1. 为 Onboarding Token 入口建立独立的设备 Lambda 组合根：
   - 路由 `POST /api/v1/device/onboarding/request` 与 `GET /api/v1/device/onboarding/status`；
   - 注入 Prisma、共享限频、SecurePackageService、ProvisioningService、MQTT Endpoint；
   - 不经过 Cognito 管理认证；
   - 明确定义并测试 `onCommitted` 的适配语义，确保包清理与 Token 核销不会被静默丢弃。
2. 为 Ingestion Worker 提供真实 Lambda entry，接入认证、Schema 校验、dispatcher 和 Heartbeat Handler，替换 501 占位代码；新增 SQS event → Heartbeat → Onboarded 的组合根测试。
3. 为 `evaluateOnboardingDeadlines` 建立独立 Lambda entry 与 EventBridge 周期任务，授予最小 DB/KMS/IoT 撤证权限；增加 CDK 模板断言，禁止再次退化为占位 Handler。
4. 在首个 Heartbeat 迁移事务中锁定并检查当前 APPROVED 申请及截止时间；`occurredAt/now >= onboardingDeadlineAt` 必须按 DEC-017 拒绝并进入同一超时状态机，不能等待异步 evaluator。新增“边界后 Heartbeat 先于 evaluator 到达”的确定性负测及并发竞态测试。

### 4.2 P1：收敛协议与可靠性

1. 以 `docs/Device-Cloud-Communication-Design-解析.md` 和 `contracts/rest/device-onboarding-api.json` 为准修正实际响应：
   - Request 返回顶层 `{requestId,status}`；
   - Status PENDING 只返回 `{status}`，REJECTED 使用 `reason`；
   - APPROVED 使用顶层 `deviceId` 和嵌套 `certificate/mqtt/configuration`；
   - 移除 Status 的 `serialNumber` Query 要求，由已认证 Token 的绑定上下文定位申请。
2. 将“审批成功后签发”改为持久化驱动：推荐在审批事务中写 Outbox/Provisioning Job，Worker 幂等消费；为 APPROVED 且无可领取包的记录提供扫描与重试，记录 attempt、lastError、nextRetryAt 和告警。
3. 对 AWS 证书创建到数据库落库之间增加补偿凭证：至少在失败路径立即撤销新证书，并用可对账的 operation/request tag 或持久化 provisioning attempt 支持崩溃恢复。
