## 一、任务完成概况

### 1.1 总体结论

**严格实际完成率：0/5（0%），Gate 结论：FAIL / NOT ACCEPTED。**

五项任务都有实质性的 TypeScript/React 模块、开发文档和测试，FE-01～05 聚焦测试 **13 files / 119 tests PASS**，整个 Admin Web 测试 **23 files / 235 tests PASS**，全仓 `pnpm verify` 也以 **1576/1576 tests PASS** 结束。但当前 `apps/admin-web` 仍是编译为 JS/声明文件的组件库，不是可启动、可访问、可部署的管理后台应用：

1. `apps/admin-web/package.json` 没有 Next.js、路由器或 `dev/start` 脚本，`build` 仅执行 `tsc`；仓库没有 Admin Web 的 `page/layout`、HTML、`createRoot`/`hydrateRoot` 入口，也没有静态站点/SSR 部署接线。产物只有 `.js/.d.ts/.map`，没有浏览器入口或页面资产。
2. `resolveRoute`、`SessionManager`、`createApiClient`、`AppShell` 和所有业务页面均未在组合根中装配；页面数据、权限布尔值和动作回调全部由外部 props 注入，但仓库内不存在该集成层。因此无法实际登录、导航、装载 API 数据或验证 401/403 后的页面跳转。
3. 没有 Playwright/Cypress/Vitest Browser 等真实浏览器 E2E。FE-03 明确要求的角色隔离 E2E、FE-05 明确要求的 CRUD E2E 均未执行；FE-01 的路由守卫和 FE-02 的响应式/无障碍仅在纯函数、jsdom 或 CSS 字符串层验证。
4. 负向探针复现 FE-03 核心验收失败：构造 `connectivity=OFFLINE`、`licenseStatus=null` 且服务端 `actions.allowed=true` 的卡片后，START 与升级按钮均未禁用。当前 Dashboard 只消费 Command 的 `allowed`，不把离线状态纳入门控；升级入口完全不消费 OTA eligibility/denyReason。
5. FE-04 明确要求的“录入人”和“证书包状态”被开发文档降级为 Defer 并从页面删除；私钥验收只检查了 DOM 文本，没有任务要求的网络快照检查。

因此，本报告不把“组件库源码存在”“119 个聚焦测试通过”或“`tsc` 构建成功”计为任务完成。五项均至少命中共同阻塞项，且 FE-03/04/05 另有任务级验收缺口。

| M-04 | `FE-04` / 路由跳转 | 批准后导航含 query string，`findRoute` 对完整字符串做精确比较；负向探针返回 `not-found` | 集成层若直接把 location path+query 交给守卫，批准后会落入 404；需明确 pathname/query 解析契约 |
| M-05 | `FE-02`～`FE-05` / 样式与响应式 | 只有壳层 CSS；Dashboard、表格、对话框、Customer/Site/Onboarding 大量 class 无样式，且无真实视口测试 | ≤768px 表格、表单、卡片和对话框可能溢出或不可操作；当前 CSS 字符串测试不能证明布局可用 |

### 3.5 低危

| ID | 所属模块 | 具体表现 | 影响范围 |
|---|---|---|---|
| L-01 | `docs/dev/FE-01～05` / 状态可信度 | 多个验收项标为 ✅，同时正文承认无路由/数据集成、无 E2E；FE-03 仍写 FE-12/18“尚未交付”，与当前仓库历史不一致；FE-05 将组件测试表述为 CRUD 完成 | 后续评审容易把模块级单测误读为实际任务完成，降低开发文档可信度 |
| L-02 | `FE-02`、`FE-05` / Dialog 无障碍 | Modal/ConfirmDialog 支持 Esc 和焦点回收，但未限制 Tab/Shift+Tab 焦点在 `aria-modal` 内 | 键盘用户可把焦点移到遮罩后的页面控件；“键盘操作可用”只部分成立 |
| L-03 | `FE-02`～`FE-05` / 游标分页 | CursorTable 支持上一页端口，但 Onboarding/Customer/Site 页面不传 `hasPrevPage/onPrevPage`，实际只可向后翻页 | 用户进入后续页后不能在表格内返回上一页，影响列表操作效率与可恢复性 |

### 3.6 风险归纳

1. **首要风险是组件库被误当成 Web 应用**：当前代码适合作为实现基础，但没有可运行入口与组合根，无法承载任何页面级验收。
2. **绿色 Gate 存在明显范围差异**：119 个聚焦测试和全仓 1576 个测试都是真实绿灯，但没有覆盖浏览器路由、真实 API、响应式布局、网络敏感字段或 E2E。
3. **动作授权存在双重分叉**：Dashboard Command 没有离线门控，OTA 没有 eligibility；其他写操作依赖未绑定的布尔 props，不能证明“服务端结果决定按钮可用性”。
4. **任务内容被文档自行降级**：录入人、证书包状态、角色隔离 E2E 和 CRUD E2E 属原任务明确内容，开发文档无权仅以 Defer/QA 边界将其计为完成。
5. **真实安全证据不足**：私钥未进入 DOM 不等于未进入网络；无实际 Cognito/API 联调也不能证明浏览器会话和租户隔离。

## 四、整改建议

### P0：建立可运行管理后台与组合根

1. 在 `apps/admin-web` 落地正式 React/Next.js 应用：增加 page/layout 或等效浏览器入口、路由器、`dev/build/start`、环境配置校验和浏览器产物；不要继续把 `tsc` 组件库输出称为 Web 应用构建。
2. 建立唯一组合根：实例化 Cognito client、SessionManager、ApiClient；订阅 `sessionManager.onClear` 跳转登录；把 `resolveRoute` 绑定真实 pathname；明确 query/hash 解析；按 routeId 装配 Login、403、Dashboard、Onboarding、Customer、Site 页面。
3. 为每个页面建立数据 controller/hooks：装载 API、游标栈、刷新、stale、partial-error、写操作、Toast；从集中权限/服务端 capability 派生按钮状态，不允许页面调用方任意传裸 `canWrite/canReview`。
4. 增加前端交付 Gate，至少失败关闭检查：可执行入口、routeId→page 双向覆盖、页面 API operationId、CSS/静态资产构建和浏览器 smoke test；避免组件测试继续假绿。

### P1：关闭业务、安全和 E2E 缺口

5. FE-03 将离线门控纳入服务端 Dashboard action capability 或前端在服务端 capability 基础上追加失败关闭；Command/OTA 共用可版本化 capability 模型。OTA 入口必须携 `allowed/denyReason`，无权、无 Entitlement、离线或非法状态时禁用并显示原因。
6. 为 Dashboard 定义正式部分失败契约（例如分区 `status/errorCode/requestId/dataUpdatedAt`），页面分别渲染指标、告警和设备卡片错误，不把后端失败伪装为空数据。
7. 扩展 BE-ONB-02 正式契约，为录入人和管理端可见的证书流程状态提供不含私钥的数据源；同步 OpenAPI、DTO、页面和测试。若产品确实决定不展示，应先修改任务清单/决策，而非在实现文档单方面 Defer。
8. Onboarding 增加 transport/network snapshot 测试，对列表、详情、approve/reject 的原始响应与请求记录检查 `privateKey/private_key/token/PEM`；DOM 零命中作为第二层，而非唯一层。
9. 落地 Playwright（或等效）E2E：五角色菜单/路由、无 Token、401 刷新失败退出、403 页面、Customer scope 隔离、Dashboard 离线/无授权动作、Onboarding 并发审批、Customer/Site CRUD、非法时区、关联停用和 409 冲突。

### P2：补齐响应式、无障碍与文档可信度

10. 为通用组件和 FE-03～05 页面补齐 CSS/设计 tokens；在 1440px、768px、375px 真实浏览器视口验证卡片、表格横向策略、抽屉、表单和对话框。
11. Dialog 实现焦点陷阱、初始焦点规则、Tab/Shift+Tab 循环与遮罩背景 inert；页面接入用户时区、数据时间和 stale；列表 controller 维护游标栈以支持上一页。
12. 更新 `docs/dev/FE-01～05`：使用 `module implemented / app integrated / browser verified / target integrated` 分层状态；删除陈旧依赖描述；在真实 E2E 未通过前，不把相关验收项标为 ✅。
13. 整改完成后按顺序复核：聚焦单元/组件测试 → 前端 build/smoke → 浏览器 E2E → 全仓 `pnpm verify` → 目标 Cognito/Admin API 联调。每层单独记录结果和边界，最终五项仅在全部自身验收闭合后计入 PASS。

**最终严格结论：FE-01～FE-05 实际完成 0/5（0%），FAIL / NOT ACCEPTED。现有模块与测试可作为整改基础，但不能作为可运行管理后台或 E2E 验收凭据。**
