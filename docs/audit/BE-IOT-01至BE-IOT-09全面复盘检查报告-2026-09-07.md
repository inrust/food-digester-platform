## 3. 问题清单及风险分析

### 3.1 汇总

| 严重度 | 数量 | 主要影响 |
|---|---:|---|
| 阻塞级 | 1 | Media 上行生产链完全不可用 |
| 高危 | 5 | 批处理可靠性、Onboarding/轮换、原始审计归档、Command 超时、Media 会话安全 |
| 中危 | 6 | Envelope 信任边界、gap/聚合/报告并发正确性、目标环境证据 |
| 低危 | 1 | 任务开发文档可导航性与证据可复核性 |
| 合计 | 13 | 当前不满足 BE-IOT-01～09 整体验收 |

### 3.2 阻塞级

#### B-01 Media 上行已配置进 Ingress，但生产 dispatcher 明确无 Handler（P0 已关闭）

- **所属模块**：BE-IOT-09、BE-IOT-01、`infra`、`apps/ingestion-worker/src/ingest/dispatcher.ts`、`apps/cloud-api/src/media/service.ts`
- **具体表现**：CDK 为 media 创建第 8 条 Rule，并发送到与其他上行相同的 Ingress；dispatcher 仅注册 7 个 Handler，media 必然抛 `NO_HANDLER` 并进入 Quarantine。BE-IOT-08 文档声称 media 应走另一通道，但仓库没有该路由。
- **影响范围**：所有生产 Media Metadata 上行；S3 对象即使已正确上传，也无法通过 IoT 链路登记为 MediaObject。
- **证据**：dispatcher 第 39～53 行；CDK `createIotIngestionRules` 对全部 `UPLINK_TOPIC_TYPES` 循环；既有 `ack-dispatch.test.ts` 反而将 media→NO_HANDLER 锁成预期行为。
- **风险**：BE-IOT-09 交付物缺失，摄像头最新媒体链路不可用，不能发布。

### 3.3 高危

#### H-01 Quarantine Sink 失败破坏 partial batch failure（P0 已关闭）

- **所属模块**：BE-IOT-02 / SQS Batch Handler
- **具体表现**：捕获不可重试错误后直接 `await deps.quarantine.send(...)`；该 AWS 调用失败时异常逃出整个 Handler，后续记录不再处理，也没有返回当前 item 的 `batchItemFailures`。
- **影响范围**：同一 SQS 批次中的所有合法/非法记录；可能重复业务处理、增加重试风暴并扩大 DLQ。
- **负向探针**：两条坏记录 + Quarantine sink 抛错，实际为整个 Promise reject，而非两条 item failure。

#### H-02 Heartbeat 副作用失败后被 receipt 永久短路（P0 已关闭）

- **所属模块**：BE-IOT-04 / BE-ONB-04 / BE-CERT-02～03
- **具体表现**：latest state + receipt 事务先提交；随后才执行 Onboarding/轮换确认。若 `destroyPackage`、DB 或审计步骤瞬时失败，SQS 会重试同一消息，但 receipt 返回 `DUPLICATE_SKIPPED` 后立即 return，不再执行扩展点。
- **影响范围**：首个 Heartbeat 完成 Onboarding、证书轮换确认与旧证撤销；设备可能有最新在线状态却长期停在 OnboardingApproved 或轮换未完成。
- **负向探针**：首次 `destroyPackage` 注入瞬时失败，第二次处理同消息返回 `onboardingTransitioned=false`，设备仍为 OnboardingApproved。

#### H-03 DEC-013 兼容 Telemetry 的“原始归档”被规范化内容替代（P1 已关闭）

- **所属模块**：BE-IOT-02、BE-IOT-05、Raw Archive/Replay
- **具体表现**：管线把 `parsed.payload` 替换为 `normalizeMqttPayload(...)` 的副本；Telemetry Handler 随后把该规范化 Payload 标作“原始 Payload”写入 outbox。兼容字段 `motorCurrentAmp` 会变成 `currentAmp`。
- **影响范围**：兼容期内全部旧格式 Telemetry；S3 不再保存实际设备原文。原始 `audit.hash` 是对规范化前 `{meta,data}` 计算的，归档后 Payload 与 hash 可能不匹配，Replay 也可能被 `AUDIT_HASH_MISMATCH` 隔离。
- **风险**：审计可验证性、取证、重放和“原始 payload 必须归档”的明确验收条款均受影响。

#### H-04 已过 `expiresAt` 但尚为 PUBLISHED 的 Command ACK 被接受（P1 已关闭）

- **所属模块**：BE-IOT-08 / `signals/ack.ts`
- **具体表现**：ACK 查询结构不读取 `expiresAt`，只依据当前 status 调 `classifyAck`。若 timeout evaluator 尚未把状态推进到 TIMED_OUT，晚到 ACK 会把过期命令改为 SUCCEEDED。
- **影响范围**：调度延迟或并发窗口内的所有 Command；设备端过期执行会被误认成功。
- **负向探针**：`expiresAt=00:01`、ACK at `00:02`、status=PUBLISHED，实际返回 `toStatus=SUCCEEDED`。

#### H-05 ISSUED Media 会话超过 URL 有效期仍可登记对象（P0 已关闭）

- **所属模块**：BE-IOT-09 / BE-MED-01 Media Metadata Service
- **具体表现**：服务只检查 `session.status === 'ISSUED'`，没有比较 `presignedUrlExpiresAt` 与当前时间。没有 sweeper 时，过期会话仍保持 ISSUED。
- **影响范围**：全部未被后台清扫的过期上传会话；违反“过期会话拒绝”的明确验收要求。
- **负向探针**：会话 00:01 过期、00:02 上报，实际 `applied=true` 并创建 MediaObject。

### 3.4 中危

#### M-01 Envelope 解析器静默删除所有额外 `iot*` 顶层字段（P1 已关闭）

- **所属模块**：BE-IOT-01～02 / Envelope 信任边界
- **具体表现**：解析器用 `!key.startsWith('iot')` 重建 Payload，而不是只排除五个 Rule 保留字段。攻击或漂移字段如 `iotInjected` 在 Schema 校验前消失，封闭 Payload Schema 无法拒绝。
- **影响范围**：入口契约漂移检测与原文保留；可能掩盖 IoT Rule 键碰撞和异常设备行为。
- **负向探针**：携带 `iotInjected` 的 Envelope 被解析成功且该字段消失。

#### M-02 `iotTopic` 的设备段与 `iotDeviceId` 未做交叉校验（P1 已关闭）

- **所属模块**：BE-IOT-02 / Identity
- **具体表现**：只校验 Topic type 与 `iotType`，没有校验 `iotTopic.split('/')[2] === iotDeviceId`。当前身份解析只继续使用 `iotDeviceId`。
- **影响范围**：Replay、人工重投、错误 Rule 模板或队列注入场景中的上下文一致性；审计记录 Topic 与台账身份可能相互矛盾。
- **负向探针**：Topic 为 `dev-topic`、`iotDeviceId=dev-context` 时 `parseEnvelope` 未拒绝。

#### M-03 gap 检测在不同 seq 并发首处理时可能漏记（P1 已关闭）

- **所属模块**：BE-IOT-03 / `ingest/gap.ts`
- **具体表现**：每个 receipt 事务通过查询当前较小最大 seq 后追加 gap，没有 device+topic 级锁或可序列化约束；源码已注明极端交错可能漏记。
- **影响范围**：高并发同设备同 Topic 的乱序可观测性，缺口状态查询可能误报“无缺口”。

#### M-04 Telemetry 同窗口并发采用无版本条件的读改写（P1 已关闭）

- **所属模块**：BE-IOT-05 / `telemetry/repository.ts`
- **具体表现**：读 `sampleCount/metrics` 后直接 update；并发事务可基于相同旧值各自写回，后写覆盖先写。源码明确注明可能丢失增量。
- **影响范围**：hourly 样本数、平均值、最小/最大值及后续 ESG 汇总；Replay 可以修复不代表在线结果满足验收。

#### M-05 Report 期间重叠只有先查后插，没有排他约束（P1 已关闭）

- **所属模块**：BE-IOT-06 / Report Repository / Database
- **具体表现**：两个不同 `periodStartTime` 的重叠事务可同时查不到对方并分别插入；现有唯一键只覆盖 `(deviceId, reportType, periodStartTime)`，不会产生文档声称的 P2002。
- **影响范围**：Cycle/Hourly/Daily 报告期间完整性、ESG 查询与汇总；违反“期间重叠被拒绝”。

#### M-06 缺少目标 AWS 环境 IoT Rule 验收证据（P2 Gate 已落地，实跑回执仍 OPEN）

- **所属模块**：BE-IOT-01 / 部署证据
- **具体表现**：本轮仅有 CDK synth 模板断言；没有 8 Topic 真投递、未知 Topic 不投递、Rule Action 失败进入独立 Error Queue 的目标环境证据。
- **影响范围**：BE-IOT-01 只能认定本地条件完成，不能证明 AWS 账号内真实配置与运行行为。
- **性质**：证据缺口，不等同于已确认的 IaC 代码缺陷。

### 3.5 低危

## 4. 整改建议

### 4.1 P0：先解除发布阻塞

1. **接通 BE-IOT-09 生产链**：在 ingestion-worker 内新增 Media Handler 适配器，复用 BE-MED-01 的校验核心，并注册到 `createBusinessDispatcher`；统一使用 BE-IOT-03 receipt/事务语义；删除“另有路由”但无 IaC 的文档假设。
2. **修复过期 Media 会话**：Metadata 处理时原子校验 `status=ISSUED AND presignedUrlExpiresAt > now`；过期时返回稳定隔离原因并可幂等转 EXPIRED。新增 SQS→pipeline→dispatcher→Media→RDS 端到端测试。
3. **修复 Heartbeat 可重试性**：将 receipt、latest state 与 Onboarding/轮换确认纳入可恢复的同一业务状态机，或为副作用建立独立 outbox/job；重复 receipt 不能无条件跳过尚未完成的扩展点。
4. **修复 Quarantine partial failure**：Quarantine send 失败时只把当前 `messageId` 加入 `batchItemFailures` 并继续处理其他记录；补充 Quarantine 部分失败、多条混合批次测试。

### 4.2 P1：恢复契约、超时和数据正确性

1. **保留 raw 与 normalized 双视图**：`ValidatedMessage` 同时携带不可变 `rawPayload/rawBody` 与 `normalizedPayload`；业务校验/映射用 normalized，receipt 与 Raw Archive 明确定义使用哪个 Hash，S3 必须保存实际原文并能复算原始 audit.hash。
2. **ACK 以事件时间和当前时间双重校验过期**：查询 `expiresAt`，在状态仍为 PUBLISHED 但已超时的竞态窗口走确定的 late/expired 异常路径，禁止更新成功；补充边界时刻和 evaluator 并发测试。
3. **Envelope 失败关闭**：仅剥离五个保留字段；额外顶层字段交给 MQTT Schema 拒绝；强制 Topic device/type 与 `iotDeviceId/iotType` 全量一致。
4. **并发正确性**：Telemetry 使用数据库原子累计、乐观版本重试或 device+bucket 锁；gap 使用 device+topic advisory lock/串行化；Report 使用 PostgreSQL range exclusion constraint 或等价串行化锁。

4. 在隔离 AWS 测试环境补齐 BE-IOT-01 与 QA-03 证据：8 Topic、未知 Topic、Rule Error Action、partial failure、Quarantine、receipt、RDS/outbox、Archive SQS/S3 原文一致性。
